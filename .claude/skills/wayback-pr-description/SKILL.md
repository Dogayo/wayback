# Описание пул-реквеста

Описание читает человек перед ревью. Его задача — за полминуты объяснить,
**что изменилось и зачем**, а не пересказать дифф. Детали ревьюер увидит в коде.

## База сравнения

По умолчанию — `develop`. Другую базу бери, только если пользователь назвал её явно.

```bash
git fetch origin develop --quiet
git log origin/develop..HEAD --oneline
git diff origin/develop...HEAD --stat
```

Если `origin/develop` нет — используй локальную `develop`; если и её нет,
скажи об этом и спроси базу, не подставляя `main` молча.

## Порядок действий

1. Собери фактический дифф командами выше. Пиши только то, что в нём есть —
   не додумывай намерения и не описывай планы на будущее.
2. Определи одну главную мысль ветки: что она даёт проекту. Это заголовок.
3. Сгруппируй изменения по смыслу, а не по файлам. Пять правок в одном слое —
   один пункт, а не пять.
4. Отфильтруй шум: форматирование, переименования, мелкие правки импортов
   в описание не идут, если это не суть ветки.
5. Отдай результат готовым markdown-текстом, который можно вставить в PR.
   PR не создавай и не пушь — только если пользователь попросил.

## Формат

```markdown
## Что сделано

Одно-два предложения: суть ветки и зачем это нужно.

## Изменения

- Добавлен экран списка сохранённых точек.
- Расчёт расстояния и азимута вынесен в `core/utils`.
- Ошибки хранилища теперь доходят до UI как локализованный текст.

## Как проверить

1. Открыть экран списка.
2. Удалить точку — она исчезает и не возвращается после перезапуска.
```

Правила по секциям:

- `## Что сделано` — обязательна.
- `## Изменения` — обязательна, 3–7 пунктов. Больше — значит группировка не доделана.
- `## Как проверить` — только если проверка неочевидна и есть что делать руками.
- Пустых секций не бывает. Нечего написать — секции нет.
- Секцию с рисками или незакрытыми хвостами добавляй отдельным абзацем в конце,
  без заголовка, и только если они действительно есть.

## Как писать пункты

- Русский язык, одна строка, до ~12 слов.
- Глагол в прошедшем времени, средний род: «Добавлен», «Вынесен», «Исправлено».
- Один пункт — одно изменение, без склейки через «и».
- Технический уровень допустим (в отличие от чейнджлога): здесь читатель —
  разработчик, можно называть слои и модули.
- Имена файлов — только когда без них непонятно, и тогда путём, а не классом.
- Без оценок и маркетинга: «улучшено», «стало удобнее», «отличный рефакторинг».

Хорошо:
- `Добавлен Bloc экрана навигации с состояниями loading/content/error.`
- `Маппинг ошибок перенесён в реализацию репозитория.`

Плохо:
- `Много изменений в features.` — не говорит ничего.
- `Правки по 14 файлам.` — считает файлы, а не смысл.
- `Отрефакторил, стало сильно чище.` — оценка вместо факта.

## Проверка перед завершением

- База сравнения — `develop`, если пользователь не указал другую.
- Каждый пункт подтверждается диффом.
- Нет пересказа построчных правок и нет упоминаний, чего в ветке нет.
- Текст читается за полминуты.
